## 1. The headline

**We were reporting an MCC the thesis does not define.** Every detection number
produced before today — the Q1-Q6 macro of 0.219, the Q6 figure of 0.264, all the
per-variant tables — came from the inline **per-node** confusion matrix in
`routing.cc`. `main.tex` defines M1 over **per-RSU, non-overlapping 10 s blocks**
(`eq:eval_dedup`). There is no per-node evaluation anywhere in the thesis.

The simulator now emits the window grid the paper requires, and the first
paper-defined M1 is:

```
Q6 full system, 90 s, 60 %, seed 1
AGGREGATE M1 = 0.2721      FPR (RSU) = 65.16 %   [hard gate <= 1 %  -> VIOLATED]

  A1 0.3676   A2 0.3118   A3 0.0000   A4 0.5159
  A5 0.2366   A6 0.2784   A7 0.2307   A8 0.2421
```

**Recall is not the problem. Precision is.** DR runs 80.7-98.6 %; A5-A8 detect
95-99 % of attacks — better than the previously published table. Every point of MCC
is lost to false positives.

### Three constraints when computing M1

1. **RSU rows only.** `eq:eval_dedup` indexes by `(k)`, the RSU. There is no OBU
   ground truth in the paper and none should be invented — `lrad_obu()` fires at the
   *receiving* vehicle (the victim), and its suspicion is attributed to the RSU.
2. **Non-overlapping blocks.** The emitter writes a stride-5 overlapping grid; take
   every other window. The paper is explicit that dedup "materially affects all figures".
3. **Exclude warm-up** (`w_start >= 30`) per `eq:theta_adapt`.

`m1_from_detector_windows.py` handles (1) only; apply (2) and (3) yourself.

## 3. Why the old 0.895 table is not comparable

`evaluator.py`'s 0.895 scores **the LSTM alone**, offline, with warm-up-adapted
per-RSU thresholds and deduplication. `D_RSU` is
`S2f ∨ S5 ∨ S6 ∨ S7 ∨ S8 ∨ flag_LSTM` — and **OR-ing detectors monotonically
increases false positives**. The composite inherits every LSTM false positive on
top of the signatures' own. DR is comparable between the two (80-99 % vs 84-93 %);
only FPR diverges (40-86 % vs 0.0-1.0 %).

Nothing regressed. Three different things were being measured.

## 4. `eq:theta_adapt` — found missing, implemented, MIXED result

### The cause

`main.tex:3425` specifies online threshold adaptation:

```
θ^(k)_adapted = max( θ^(k),  μ_warmup^(k) + z·σ_warmup^(k) ),   z = 3.5
```

Commit `77318f5` ("gate LSTM off for S3/S4, add online threshold warm-up
adaptation") implemented it in **`evaluator.py` only** — the offline scorer.
`scratch/lstm_inference.h` is not in that commit. The live detector has always
decided with the static per-RSU θ baked into `lstm_weights_cpp.bin`.

So the reported A2 improvement (FPR 2.42 % -> 1.00 %) was an **offline** result the
simulator never reproduced. It is also a spec-compliance gap, not just a missed
optimisation: the thesis defines this as part of the detector.

### The fix

Implemented in `lstm_inference.h`: per-RSU warm-up accumulators, then at the first
evaluation after 30 s, `θ_adapted = max(θ_base, μ + 3.5σ)` computed once and used
thereafter. Base θ is used *during* warm-up (the equation defines the threshold; the
"warm-up excluded" sentence is an evaluation instruction, not a detector one).
`lstm_in_warmup()` is exposed so the evaluation path can honour that exclusion.

### The measured result — read this before quoting it

Paper M1, RSU, non-overlapping, warm-up excluded. 90 s, 60 %, seed 1, same seed
both arms:

| | MCC base -> adapt | Δ | FPR | DR | FP removed |
|---|---|---|---|---|---|
| A1 | 0.3810 -> 0.3876 | +0.007 | 54.4 -> 51.9 % | 88.8 -> 87.5 % | 4 |
| **A2** | 0.2856 -> 0.2815 | **-0.004** | 43.9 -> 39.4 % | **76.4 -> 72.4 %** | 3 |
| A5 | 0.2357 -> 0.3476 | +0.112 | 91.2 -> 81.6 % | 100 -> 100 % | 12 |
| A7 | 0.2357 -> 0.4017 | +0.166 | 91.2 -> 76.0 % | 100 -> 100 % | 19 |

**Mean +0.070, but driven entirely by A5/A7. A2 REGRESSED** — and A2 is the exact
variant the offline claim was measured on.

**Why:** the fix is a trade, never free. Raising θ removes false positives but also
loses any true positive whose score sat between the old and new threshold. The
discriminator is **score separation**:

- **A5/A7** (hidden forwarding, large reconstruction error) — TPs sit far above θ,
  so raising it removes only FPs. Large gain, zero recall cost.
- **A1/A2** (timing delay, subtle signal) — TPs sit just above θ, so raising it
  costs recall about as fast as it gains precision. A2 nets negative.

Two predictions that turned out **wrong**, recorded so they are not repeated:

- `evaluator.py`'s docstring says "A5-A8 (no seed-variance problem) essentially
  unchanged". Live, A5/A7 improved *most*.
- "LSTM share of FP mass" does not predict the gain either: A1 is 90 % LSTM-owned
  and gained almost nothing.

### Recommendation

**Keep it** — it is spec-mandated, and it is net positive (+0.070 mean). But do not
present it as a uniform improvement. Consider making the adaptation **per-variant
opt-out**, or revisit `z = 3.5` for the timing variants, once the LSTM is retrained
— the current θ is calibrated on a model trained on mostly-dead features (§5), so
this trade may look different afterwards.

## 5. LSTM tier — observations and what to change

### The model in production

Trained **2026-07-31 02:28** on data collected **2026-07-08/09**. Every correction
landed **2026-08-03/04**. **The live model has never seen a single fix.**

### Six of ten features were constant during training

The exported scaler's `std` is exactly 1.0 on six features — sklearn's zero-variance
fallback:

| feature | std | status today |
|---|---|---|
| `delta_t` | 0.0144 | live |
| **`lambda_PI`** | **1.0** | **STILL DEAD** |
| `U_TCAM` | 0.0352 | live |
| `zkp_delay_fail` | **1.0** | fixed (295 rows) |
| `zkp_hop_fail` | **1.0** | fixed (613/440 rows) |
| `rho` | 10.61 | live |
| `v_bar` | 5.14 | live |
| `d_div` | **1.0** | fixed (26 distinct) |
| `a_tp` | **1.0** | fixed (31 distinct) |
| `r_anom` | **1.0** | fixed (126 distinct) |

The model was effectively trained on **four** features, two of which (`rho`,
`v_bar`) are pure mobility. It learned "unusual density/speed ⇒ anomaly". That is
why it produces 828 false positives against 65 true positives.

### `lambda_PI` is still dead — FIX BEFORE COLLECTING

`g_slowpath_hit_count` has one increment site (`routing.cc:121303`), double-gated:

```cpp
if ((active_attack_variant == 2 || active_attack_variant == 3) &&   // A3/A4 only
    current_hop >= N_Vehicles &&
    g_tcam_rule_count[current_hop] >= TCAM_CAPACITY)                // table FULL only
```

Both gates are fatal. It fires only on A3/A4, only at TCAM capacity (measured max
utilisation 0.245 — never reached), and **can never fire in a benign run**, which is
exactly why training saw zero variance. Meanwhile S4 reports `λ_PI = 180.0` from a
*different* counter, `g_packetin_count`.

**The LSTM is reading the wrong counter.** Point the feature at `g_packetin_count`.
~15 minutes. **Do this before the collection run**, or you retrain with a dead
feature again and repeat the failure that invalidated the last dataset.

### LSTM attribution — needs a supervisor ruling

LSTM detections are attributed to `prev_sender`. The signal is **per-RSU**
(`D_LSTM^(k)`), so blaming whichever node last sent a packet is near-arbitrary:

| | TP | FP | precision |
|---|---|---|---|
| control-plane (A1, A3, A5, A7) | 9 | 595 | **1.5 %** |
| data-plane (A2, A4, A6, A8) | 56 | 233 | **19.4 %** |

A 13x split. For CP attacks ground truth marks RSUs, never vehicles, so blaming a
vehicle is a guaranteed false positive. This is the same bug class already fixed for
S1 (which now attributes to `N_Vehicles + assoc_rsu_local_idx`).

**But `main.tex:2579-2581` says "Data-plane or LSTM: attacker is vehicle/RSU"**, so
the vehicle attribution may be spec-faithful. If so the spec has a per-RSU signal
attributed to a vehicle, which is a spec-level mismatch. **Supervisor decision.**

### Ordered LSTM work

1. **`lambda_PI` -> `g_packetin_count`** — 15 min, blocks nothing, must precede (2)
2. **Retrain** — unblocked; pre-flight passed 2026-08-06 (see `LSTM_FULL_PICTURE.md` §5)
3. **Re-run AB3** — currently invalid; it ablates features that were dead in training
4. **Attribution** — supervisor decision
5. **Revisit `z = 3.5`** for timing variants once retrained (§4)

## 7. Known limitation: per-component tracking saturates

Source attribution rides on `is_detected_node[][]`, a **sticky latch** — once a node
is flagged it stays flagged. So "828 nodes ever falsely flagged by the LSTM" is a set
that only grows and **cannot show improvement**. Measured: after `eq:theta_adapt`,
per-node LSTM FPs moved 196->193 (A5) and 199->197 (A7), while paper M1 improved
+0.112 and +0.166 on the same runs.

The latch is **correct** for its real purposes (M4 needs first-detection time;
attribution is a set-membership question) — do not "fix" it.

**If you want component-level improvement tracking, add a `source` bitmask column to
`detector_windows.csv`.** Then per-component FP rates are computed on the paper's
unit and can actually move. The metrics loader only requires its six columns and
ignores extras, so it is a safe addition.

## 8. Traps that have already cost time

- **A 30 s run cannot produce M1** — warm-up exclusion removes the whole run. Use >= 90 s.
- **`detector_windows_*.csv` is overwritten** by any run with the same
  attack/pct/seed — there is no config tag in the filename. Copy the baseline aside
  before a comparison run. (Baseline for this work is preserved at
  `results_routing/baseline_static_theta/`.) The Q1-Q6 runner renames
  `MOBIGUARD_*.csv` to `_Q4`/`_Q6` for the same reason; the emitter should do the same.
- **`local_path_swap.sh` used to rewrite only `routing.cc`.** That is how commit
  `149f022` leaked local paths into 17 other files (a `git add -A` staged files the
  script never touched, and `status` reported clean because it only inspected
  `routing.cc`). Now fixed to cover all 169. **Always run `hpc` before committing.**
- **Three path conventions had accumulated**, one per machine
  (`sdvn_hidden_attacks/ns3_g13`, `nipuni`, `ns3_g13_apsari`). All normalised to the
  cluster convention in `555ea10`. Do not reintroduce a fourth.
