## The finding that matters most (verified, committed)

**The M1 window grid attributed detections to the OBSERVER, not the SUSPECT.**

Three different node identities were being conflated:

| | node referenced |
|---|---|
| detectors RECORD against | `prev_sender` -- the accused (`s5_detection.h:259`) |
| window grid MARKED | `rsu` -- the RSU processing the packet (`lrad.h:417`) |
| window TRUTH asks about | `N_Vehicles + r` -- whether THAT RSU is malicious |

A benign RSU that correctly detected a malicious neighbour scored 1 against its
own truth=0 -- penalised for detecting. The "benign nodes firing in 58/58
windows" seen all session were observers sitting next to attackers.

Measured on one 90 s A5 run, both columns from the SAME simulation:

```
observer + OR-composite : MCC 0.3118  TP=288 FP=188 FN=0 TN=36
suspect  + primary      : MCC 0.9341  TP=288 FP=17  FN=0 TN=207
```

TP and FN identical in both -- detection was always correct, only attribution
changed. Consistent with the node-level matrices, where S3-S8 all show FP=0
while their window MCC sat at 0.26-0.37.

Committed as `b718110`. The `score_primary` column carries suspect-attributed,
primary-detector-only firings; the original `score` column is untouched.

**This supersedes two earlier diagnoses sent to the supervisor** -- OR-composite
pollution from S2, and dormant-window truth (Decision 4). Both effects are
real; neither was dominant.

### 2. S1 attribution measures one node, accuses another

`_delta_p` is the per-hop delay from `_prev` (`routing.cc:122174-122185`), but
S1 records against `N_Vehicles + assoc_rsu_local_idx` -- the receiving
vehicle's associated RSU, chosen by radio proximity (`lrad.h:682-683`).

Precision 25/119 = **21.0%**, versus ~60% if attribution were merely RANDOM at
this attack rate -- i.e. actively anti-correlated with culpability.

The `assoc_rsu` choice was itself a workaround for the stale-claim bug, so
item 1 must land first.

### 3. A1 ground truth shares the same wrong key

`g_s1_gt_delay_exceeded[]` is latched on that same `sender_node_id`
(= assoc_rsu), so the dormancy gate asks "was node n someone's associated RSU
during an exceedance?" rather than "did node n delay?". Also 32 RSUs are marked
malicious (all under a compromised controller) while only 26 ever applied a
delay -- 6 are structurally undetectable.

Note the attack model: the CONTROLLER is the attacker; the RSU is explicitly
"UNAWARE it is compromised" (`selective_time_delay.h:93`). Marking the RSU is a
deliberate, documented modelling choice (`attack_variables.h:18-21`) -- detect
the observable locus, trace upstream. That part is fine; the proximity keying
is not.
